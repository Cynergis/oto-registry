# cynergis: the OTO catalog of ontologies and packs

A registry. `oto registry add <this url>` on a machine, then `oto ontology add <name>` or `oto pack add <name>`. Published by `oto ontology publish` and `oto pack publish`; the index and the marketplace are generated, do not edit them by hand. Packs install in Claude Code with `/plugin marketplace add <this url>` then `/plugin install <name>@cynergis`. The engine plugin comes from its own marketplace, added first: `/plugin marketplace add Cynergis/oto` then `/plugin install oto@cynergis-engine`; this registry carries extensions and packs of the engine, never the engine ([ADR-0009](https://github.com/Cynergis/oto/blob/main/docs/adr/0009-the-registry-carries-no-engine.md)). The catalog, a page per pack and per ontology with the sample graph drawn, is generated by `oto registry site` and published with GitHub Pages on every push.

## Releasing

Every change reaches a fresh install the same way: as a pull request here, whose merge is the release.
This registry's checks run on the pull request, and the catalog rebuilds after the merge. On a machine
that already has the marketplace, `/plugin marketplace update cynergis` picks the change up.

**The plugins that live in their own repository (`pdf-to-template`, `oto-factory`).** Raise the
version in that repository and merge to main. Its release workflow tags `v<version>`, then opens the pull
request here, "Move the <plugin> pin to v<version>", from the branch `pin/<plugin>-v<version>`, with what
changed from the plugin's changelog. A version that is not newer than the one pinned here opens nothing.

- The release workflows need the organisation secret `OTO_REGISTRY_TOKEN`: a fine-grained token limited
  to this repository, with Contents and Pull requests set to read and write (or a GitHub App's token).
- Without it they still tag, and the run says how to move the pin by hand:

  ```bash
  oto registry pin <plugin> --to https://github.com/Cynergis/oto-registry.git --repo <owner/name> \
    --plugin-ref v<version> --version <version> --body-file body.md
  gh pr create --repo Cynergis/oto-registry --head pin/<plugin>-v<version> \
    --title "Move the <plugin> pin to v<version>" --body-file body.md
  ```

- The same workflow can be run by hand from the engine's Actions tab ("registry pin"), for example for a
  release whose run failed.

**Packs and ontologies.** They are published from their source repository onto a branch of this one, then
reviewed as a pull request:

```bash
git push origin main:refs/heads/<branch>      # in a clone of this repository
oto pack publish --from <pack dir> --to https://github.com/Cynergis/oto-registry.git --ref <branch> --note "<what changed>"
```

`oto ontology publish` works the same way for an ontology. A pack that needs a newer engine waits for the
engine's pin to move first, or moves it in the same pull request.

**Packs with code.** A pack may carry code of its own under its ontology's `code/` (an architecture framework's
adapter, a command), which the engine puts on the import path when it loads what the pack's manifest
`provides` (OTO 0.14.2 or later). Such a pack carries its tests under `packs/<name>/tests`, with a conftest that
points the engine at the pack; the `pack tests` workflow runs them against the engine on every pull request.
`calm`, the FINOS architecture framework, is the first: the engine ships no framework adapter
([ADR-0008](https://github.com/Cynergis/oto/blob/main/docs/adr/0008-a-framework-is-a-pack-of-the-registry.md)).
`ddd`, the domain model, is the first domain feature to leave the engine: its storming importer and `oto ddd storm` travel
in `ontology/ddd/code` as the module `oto_ddd`, loaded through the command its manifest provides; the engine ships no
pack with tools of its own ([ADR-0010](https://github.com/Cynergis/oto/blob/main/docs/adr/0010-a-domain-feature-is-a-pack-of-the-registry.md)).
`work`, the plan with `communication` on it, is the second: `oto work` and the board's status hook are the module `oto_work`
in `ontology/work/code`, and the pack's `hooks/hooks.json` opens a Claude Code session with the inbox. `data` (the data
semantic layer: `oto data` as `oto_data`) and `policy` (access policy, on data: `oto policy`, its two build stages and its write and
read hooks as `oto_policy`, with data embedded beside it) are the last two: the engine ships no pack with tools of its own.
